# 从零实现 UDP 水平自瞄

本文按实际工程的依赖顺序说明实现方法，对应 `vpn/java/local/udp/esp/vpn/` 与 `vpn/native/vpn_bridge.c`。这里的“自瞄”指本工程的最近玩家水平跟随，不包含自动攻击。

## 1. 先建立不会干扰流量的转发链

先做透明转发，再做协议和控制逻辑。`GameVpnService` 创建本机 TUN，只将目标应用纳入 VPN；JNI 转发器通过 zdtun 管理连接。外发 socket 必须调用 VpnService.protect，避免流量再次进入自身 VPN。系统要求的前台服务通知仍需保留，不能当调试提示删除。

把收发方向、远端、两端端口和原始 UDP payload 作为一条记录传给解码线程。解码队列有容量和字节数上限，队列满时丢弃分析副本，不阻塞网络转发。

最低完成条件是应用原有网络功能仍正常。协议解析失败不能变成网络丢包。

## 2. 用自己的样本确认帧边界

不要把整个 UDP payload 直接当 protobuf。先确定传输标志、序号、校验、压缩和应用消息偏移。固定实现中，下行完整帧的应用头从偏移 10 开始，上行从偏移 14 开始；分片另有头部。应用消息头由两个大端 UInt16 构成，第一个为 3，第二个是命令号。

`GameDecoder` 先处理可唯一拆分的合并帧，再处理分片与 zstd 解压，最后分派消息。未知格式应保留未知，不能把解码错误归因于唯一猜测，也不能为增加命中率直接跳过校验。

发布包不带私人抓包。用自己的样本复核该版本的偏移和字段，不把本文常量套到其他版本。

## 3. 先确认“自己是谁”

坐标本身不能区分自己和别人。`GameDecoder.identity` 从登录和名单消息恢复本地身份、玩家实体编号及名单变化；`GameState` 按连接维护会话。

身份表和场景实体使用明确的字段关联。实体的 id1、id2、UID 不是可互换的编号，不能凭数值相似就合并。登录重置会使旧会话信息失效。

完成这一步后，快照应能明确标记 `is_player` 和 `is_local`。不唯一、字段缺失或来源不明时，不选择目标。

## 4. 恢复位置、生命值和视角

场景消息 `3/852` 包含实体与动作。位置动作 kind=1 的三个整数按自身 scale 还原为坐标；生命值 kind=31 单独更新。位置更新与 HP 更新不要求同一包到达，状态表负责合并，并按时间清理过期数据。

上行 `3/851` 的 field 3 是视角方向向量。由此可算 yaw/pitch，用于状态和投影。该消息中的向量采用本协议的定制编码，不能把所有 wire=5 都按标准 protobuf fixed32 读取。具体处理见 `GameDecoder.vector`。

`Projection` 使用视角、位置和已有相机配置完成屏幕投影。此处先验证坐标方向和轴约定，再接目标控制；否则投影错误和控制错误会混在一起。

## 5. 每次从新鲜快照选目标

`NearestTarget.fromSnapshot` 的顺序是：

1. 找到当前连接及其登录时间。
2. 检查场景新鲜度，并找到唯一的本地玩家实体。
3. 枚举同连接、名单已确认、明确不是自己的玩家。
4. 排除自身编号、相同 UID、非法坐标和零距离候选。
5. 以距离平方取最小者；距离相等时用稳定的 key 顺序决定。
6. 发布不可变目标表，记录有效期。

本实现没有额外的头部高度、敌我关系和遮挡判断。应如实描述它选的是哪个目标点，而不是称为“智能识别敌人”。

设自身位置为 S，目标位置为 T，D=T-S：

```text
distance² = Dx² + Dy² + Dz²
yaw       = atan2(Dx, Dz)
```

避免开根号可降低枚举开销；最终选中目标后再求距离与单位方向。

## 6. 区分“上报方向”和“本地镜头”

第一条改写路径是上行 `3/851` field 3。`ViewRewrite` 只替换已确认的视角向量，保留其他字段，并重建需要变化的长度、压缩层和传输校验。

但上报方向来自客户端已有相机状态。修改发送副本不等于修改产生该副本的本地状态。早期实现已出现“上行改写和发送增长，但本地镜头没有转动”的情况，因此不能停在发送成功这一步。

需要继续追踪客户端怎样消费下行场景动作。离线检查工具放在 `tools/il/`：先导出目标类和动作分派，再找旋转消费函数及相机角度的写入者。保留方法声明和跳转条件，不能仅凭函数名给入口下结论。

## 7. 接入下行水平旋转

`RotationRewrite` 处理完整、可识别的 `3/852` 帧。它严格匹配自身 category、id1、id2，然后遍历动作。

- 若已有 Rotation=2：沿用已有动作的 scale 改写四元数，保留其他动作和附加数据。
- 若自身实体已有动作但没有 Rotation：追加一个只含水平角的 Rotation 动作。
- 不创建整个实体，不新增独立网络会话，不修改其他玩家。

缺失动作的水平四元数按本工程 x/y/z/w 顺序编码：

```text
h = yaw / 2
q = (0, sin(h), 0, cos(h))
encoded[i] = round(q[i] × scale)
```

动作列表中的整数按对应的 Int64 varint 编码，不要擅自换成 ZigZag。这里的 Quaternion 与上行三维方向向量是两种不同数据结构。

早期下行方案只修改已存在的自身 Rotation，运行时长期没有命中。独立统计说明，成功解析的场景里确有其他实体 Rotation，但身份确认后的自身 Rotation 未出现。最终实现改为在已匹配的自身动作列表内补齐水平 Rotation，而不是无限等待。用户随后确认原 r12 的水平效果有效。

## 8. 处理重复包和关闭操作

重传包不能使用新的目标重新计算，否则同序号消息会得到不同内容。改写器按连接、消息类型、序号和原始字节缓存首次结果；同包重传复用首次决定。缓存有条数、容量和时间上限。

控制开关通过不可变 ViewControl 和 epoch 传递。完成计算后再次核对开关与目标有效期，防止跨线程使用已失效目标。关闭影响新包；已缓存的重传仍遵循首次决定，这一点属于现有实现语义。

流程切换、连接结束和停止 VPN 时清理会话与缓存。不要把旧连接的 id、序号或目标迁到新连接。

## 9. 收发副本必须分离

```text
原包 ──→ 有界解码队列 ──→ GameState ──→ 目标表 / ESP
  └──→ 改写器 ──→ 原生转发 / TUN
```

ESP 始终分析原始字节。若把自己改过的包再当作服务端状态，会出现“写值被读回，所以成功”的假闭环。网络校验与 TUN 递交只能证明处理链完成，不能替代用户观察到的镜头效果。

## 10. 发布前收尾

开发期间的场景计数、原包 Rotation 分类和自动日志用于定位问题；本源码发布版删除了这些界面与落盘功能。必要的启动失败、转发退出和投影错误仍向用户显示。

保留原始协议解析和改写算法，只把显示、日志与构建整理为可发布工程。每次修改后至少完成源码编译、APK 签名验证与发布清单检查；动态效果由操作者在自己的环境验证。不要用一次数值回读代替完整运行结果。
